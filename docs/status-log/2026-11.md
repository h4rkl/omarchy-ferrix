## 2026-11-24 (app sandbox hardening: cgroups, network namespace, filesystem view, seccomp, per-app uid; QEMU/mock only)

- **Scope (#10):** five increments in `ferrix-sandbox`
  (`crates/ferrix-runtime-native`, details in its README), each a separate
  commit. No physical target was touched; nothing here is Pixel 9a evidence
  (GKI options for these features are unverified there).
- **cgroups v2:** stage 1 creates and joins `ferrix.slice/app-<id>-<pid>`
  before `unshare` with `memory.max` (1 GiB default, `memory.oom.group`),
  `pids.max` (1024) and `cpu.weight` (100); the runtime removes it after
  reaping and exposes it as `RunningApp::cgroup_path()` (the spec 10 uclamp
  handle). A missing hierarchy or controller is a truthful degraded launch.
  QEMU initramfs: init mounts cgroup2 and delegates `cpu memory pids`
  (`cgroup-ready` record). pmOS: `rc_cgroup_mode="unified"` is now set
  explicitly and recorded in `image-facts.json` (not rebuilt in this run).
- **Network namespace:** new `network` capability; without it an app gets a
  namespace holding only `lo` (brought up over rtnetlink). Derived from the
  grants, so a manifest cannot widen it; Terminal is granted `network`.
  The readiness report is now connected before `unshare` because abstract
  sockets are per network namespace.
- **Filesystem view:** default `fs_view: minimal` pivots into a tmpfs root
  with read-only system directories and `/sys`, a minimal `/dev` with a
  private devpts, a writable data dir (`FERRIX_APP_DATA_DIR`), and `$HOME`
  only with the new `files-home` grant (Files, Terminal, Contacts). On the
  initramfs root the view is entered with move + `chroot`.
- **seccomp:** default-deny-dangerous filter through `seccompiler`
  (Apache-2.0 OR BSD-3-Clause, Linux-only dependency): `mount`, `unshare`,
  `setns`, namespace `clone`, `ptrace`, `bpf`, modules, `kexec`, `chroot`,
  keyring and more return `EPERM` (46 rules on aarch64); `clone3` returns
  `ENOSYS`. Escape hatch: `seccomp.allow` / `profile: unconfined` per launch
  configuration. Waydroid is not covered.
- **Per-app uid (opt-in):** `uid: per-app` maps `0 0 1` + `S S 1` in a user
  namespace (helper writes the map) and starts only the app as subuid `S`
  with no capabilities; data dir is `S:S` 0700. Not the default: `S` cannot
  reach root-owned Wayland/daemon sockets yet.
- **Guest image fix:** the initramfs root was `0700` and every file owned
  by the macOS build uid; harmless to root until a user namespace exposed
  it (`EACCES`). `qemu-build.sh` now archives with `-R 0:0` and a `0755`
  root.
- **Evidence (mock, privileged arm64 container):**
  `FERRIX_SANDBOX_TESTS=required just linux-check test -p
  ferrix-runtime-native`: 38 unit + 32 sandbox tests pass, including
  negative tests for a forbidden path, forbidden syscalls (with an
  unconfined control), no network without the grant, a refused fork loop
  under `pids.max`, an OOM group kill under `memory.max`, and a root-only
  file refused under per-app uid.
- **Evidence (QEMU):** `just qemu-build && just qemu-check` passed
  (`check-passed`, `sandbox_selftest: ok`); the guest's
  `sandbox-selftest.sh` reported `sandbox-denied` ok for forbidden-path,
  forbidden-syscall, no-network, pids-limit, memory-limit (137) and
  per-app-uid. `just qemu-gesture-check` passed with Home and Messages under
  the new defaults (`degraded: false`); an agent session showed Terminal
  (private pty, `$HOME` via `files-home`, no `/var`) and Files listing the
  real home, frames inspected. `just qemu-scenario-check`: 33/33 passed.
  The scenario harness has no app-launch step, so the sandbox proof lives
  in `qemu-check` rather than a scenario.
- **Limitations:** per-app uid is opt-in only; granted apps share the
  launcher network (no veth/nftables); no cgroup freezing; Contacts holds
  `files-home` until a document portal (#11); Pixel 9a re-verification
  (GKI config) is still open.

## 2026-11-24 (Pixel 9a sensors, power/thermal, camera, GNSS, NFC and fingerprint feasibility, #9 #26 #3 #28 #29; physical:google-pixel-9a-tegu-gxq96-mp1-0 read-only + offline)

- **Scope:** target `google-pixel-9a-tegu-gxq96-mp1-0` on the Ferrix Kleaf
  dev route (`6.1.124-android14-11-ga4662a84a15f`). The physical part is two
  read-only sysfs, `/dev` and dmesg inventories the owner took on 2026-11-24.
  They are kept as ignored `out/pixel-9a/inventory-20261124.txt` and
  `inventory3-20261124.txt` and contain no serials, MACs or IMEIs. The
  offline part is the pinned Kleaf sources (manifest `893fbfd2`, read
  read-only on the builder) and a read-only `debugfs` listing of the
  hash-verified factory `vendor.img` and `vendor_dlkm.img`, made outside the
  repository. No phone, ADB, Fastboot or serial command was run by this work,
  no firmware or image bytes are committed, and no capability changes.
- **Sensors** ([`sensors-source-evidence.md`](../../targets/boards/google-pixel-9a-tegu-gxq96-mp1-0/sensors-source-evidence.md)):
  accelerometer, proximity and ambient light are all **NO-GO**. The only IIO
  devices are the two PMIC ODPM power meters. The tegu DT has no AP-side
  motion, light or proximity node, and the sensor rails belong to the AoC
  node. Stock reads the sensors through AoC firmware and the closed USF
  sub-HAL.
- **Power and thermal** ([`power-thermal-source-evidence.md`](../../targets/boards/google-pixel-9a-tegu-gxq96-mp1-0/power-thermal-source-evidence.md)):
  **GO-with-conditions** for attended, bounded sessions; **NO-GO** for
  unattended charging.
  - The kernel owns soft JEITA, the CC/CV table by temperature, termination,
    BCL, the PMIC hardware shutdown at `north_therm` 66.7 °C, and ACPM
    firmware SoC throttling. The SoC TMU zones read `mode=disabled`, which
    `gs_tmu_probe()` does by design.
  - On stock, the Pixel thermal HAL owns skin-temperature CPU, GPU and TPU
    caps, `fcc`/`dc_icl` charge throttling, `usbc-port` and the battery
    60 °C shutdown. Ferrix runs none of these, and all 29 cooling devices
    read 0.
  - `charge_stop_level` is the kernel-supported charge-limit control.
    Writing it stays owner-gated.
- **Camera** ([`camera-source-evidence.md`](../../targets/boards/google-pixel-9a-tegu-gxq96-mp1-0/camera-source-evidence.md)):
  **NO-GO**. V4L2 nodes are MFC, JPEG and the touch heatmap only, and there
  is no `/dev/media*`. The three sensors are LWIS I2C devices, and the CSIS
  link, PHY and PDMA are register windows of the `isp-fe` LWIS device that
  the closed camera HAL APEX drives. No raw Bayer V4L2 route exists for
  libcamera's simple pipeline and soft ISP.
- **GNSS** ([`gnss-source-evidence.md`](../../targets/boards/google-pixel-9a-tegu-gxq96-mp1-0/gnss-source-evidence.md)):
  **NO-GO**. The receiver is Samsung KEPLER. BETP runs over `spi_21` through
  the raw `/dev/gnss_ipc`, while firmware boot (`kepler.bin`) and dump use
  the S5300 CPIF channels `gnss_boot`/`gnss_dump`. Positions come from the
  closed `gnssd` and SLSI HAL. `bcm47765.ko` loads but binds nothing.
- **NFC and fingerprint** ([`nfc-fingerprint-source-evidence.md`](../../targets/boards/google-pixel-9a-tegu-gxq96-mp1-0/nfc-fingerprint-source-evidence.md)):
  - NFC is **GO-with-conditions for a kernel spike only**. The controller is
    an ST54L on `hsi2c_9` `0x08`, with resident firmware, exposed as a raw
    plain-NCI misc device for the closed ST HAL. The GKI has `CONFIG_NFC=m`
    but no NCI. Mainline `st-nci` speaks NDLC, so a transport, DT and neard
    spike must prove a tag read before any product claim.
  - Fingerprint is **NO-GO**. The Goodix UDFPS driver is GPIO, IRQ and power
    only (`USE_PLATFORM_BUS`), with no fingerprint SPI device visible to
    Linux. Capture and matching run in the Trusty TA `g7a.app` behind the
    closed Goodix HAL.
- **Limitations:** These are source and inventory decisions, not runtime
  proofs of absence on every boot. The AoC `revision` read `FW Revision : 0x0`
  in this capture. Each document lists the exact read-only device commands
  still wanted. Thresholds quoted from the stock thermal configuration are
  references for a future Ferrix policy, not measurements.

## 2026-11-24 (power key, screen blanking, idle timeout, power menu, backlight floor; issue #9; QEMU/mock only)

- **Scope:** spec 04 (`plans/todos/04-lifecycle-suspend-sensors.md`)
  deliverables 1, 2 and 4 on the QEMU/mock route. Nothing here is physical
  evidence. No capability status changed: the QEMU matrix stays `mocked`
  everywhere and the Pixel 9a `lifecycle` row stays `unsupported`
  (promotion is owner-gated).
- **Power key (trusted):** `ferrix-shell` takes evdev `KEY_POWER` (116) out
  of the keyboard stream before xkb or any client sees it, press and release
  alike (`crates/ferrix-shell/src/power.rs`, pure and host-tested). Short
  press toggles the screen; a hold past 600 ms opens the power menu (waking
  the screen first when off); a short press with the menu open closes it and
  turns the screen off. QEMU injects it as the `power` qcode on the
  virtio-keyboard: `just qemu-key power`, new `just qemu-key-hold power
  1000` (QMP `send-key` `hold-time`).
- **Power menu:** drawn by the compositor itself
  (`crates/ferrix-shell/src/power_menu.rs`, `ferrix-ui` canvas into a Smithay
  memory buffer); opaque `bg`, Power off / Restart / Cancel in thumb reach
  (`docs/design.md` "Power menu and screen off"). It owns all pointer and
  touch input while open; the actions go to `ferrix-core` as the typed
  `HardwareCommand::PowerAction { action }`, which calls the new
  `Lifecycle::power_action` (default `Unsupported`). The emulator accepts;
  the core then hands the action to init through `--power-marker` and the
  QEMU init powers off or reboots the guest. The Pixel 9a adapter runs
  `/sbin/poweroff` / `/sbin/reboot` (orderly OpenRC); not exercised.
- **Blanking:** screen off DPMSes the DRM output (`DrmCompositor::clear`:
  CRTC inactive, planes off), stops rendering and frame callbacks, cancels
  live client touches and pressed buttons, and sends every toplevel
  `wl_surface.leave`; while off no input reaches a client (`input-dropped`
  records the first event of each contact; motion and lifts of contacts that
  went down while off are dropped too). Wake re-commits the mode, repaints
  everything and re-enters the front toplevel (`refocus`, which no longer
  enters anything while the screen is off), so Waydroid's hwcomposer sees its
  window on the output again (ADR-008). The nested backend shows a black
  frame instead.
- **Idle timeout and inhibitors (owned by `ferrix-core`):** the core keeps
  the screen policy (`crates/ferrix-core/src/screen.rs`): the idle timeout
  (5..=3600 s or never; persisted in `--screen-state`, default
  `/var/lib/ferrix/screen.json`; profile default `[display]
  idle_timeout_secs`, `0` = never, absent = 60) and live inhibitors with a
  closed `InhibitReason` (`call`, `video`, `navigation`). Typed API in
  `ferrix-protocol`: `inhibit_blank(..) -> BlankInhibitor` (released on
  drop, `release`, or when the holder's connection closes, so a crashed app
  cannot hold the screen on), `set_idle_timeout`, `screen_policy`,
  `watch_screen_policy`. The shell enforces the effective timeout (none while
  inhibited). Mock-control verbs `set-idle-timeout`, `inhibit-blank`,
  `release-inhibit` drive it in scenarios. Settings > Display gains a
  **Screen timeout** row cycling 15 s, 30 s, 1 min, 2 min, 5 min, 10 min,
  Never, and names the holders (`kept on · call`). The QEMU and Pixel 9a
  dev profiles default to never so agent captures and the devtest loop never
  find a dark panel.
- **Backlight floor:** `MIN_BRIGHTNESS_PERCENT` (5) in
  `ferrix-hardware-api`. The core clamps product and mock-control brightness
  requests to it, the Settings rail stops there, and the Pixel adapter
  clamps too and never writes a raw 0 for a lit panel (`backlight_raw`). The
  Settings rail -> `HardwareCommand::SetBrightness` -> `Display` adapter path
  is the one the Pixel's `/sys/class/backlight` adapter implements; not
  exercised on hardware here.
- **Evidence (QEMU, TCG):** `just qemu-build`; `just qemu-check`
  (`check-passed`); `FERRIX_QEMU_SCENARIO_FRAME=1 just qemu-scenario-check`
  (`scenario-check-passed`, 34 passed, 0 failed, 59 s) including the new
  `display-power-key-blank-wake-menu` (12 steps). Its steps use the new
  scenario `service = "input"` (QMP key/tap through the real virtio-input
  path) and assert: `power-key press:short` -> `screen-power state:off` ->
  `drm-dpms state:off status:ok`; a tap while off -> `input-dropped
  kind:pointer`; wake -> `drm-dpms state:on status:presented`; a 1.2 s hold
  -> `power-key press:long` -> `power-menu state:open`; Cancel ->
  `power-menu state:closed reason:cancel`; a call inhibitor reaches the
  shell (`idle-policy inhibited:true`), its release restores
  `effective_secs:5`, and the screen blanks on its own (`screen-power
  cause:idle`). Its final frame (Phone in front, left by earlier scenarios)
  is lit and redrawn after the wake. In an agent session the captured frames
  were inspected: home; while off, QEMU's own "Display output is not active."
  placeholder (the CRTC is disabled); home again after wake; the power menu.
  Restart from the menu logged `power-action status:accepted` ->
  `power-action-init action:reboot` -> `reboot: Restarting system` -> a new
  `boot-health`. Settings > Display showed the Screen timeout row; one tap
  set 15 s (`settings-action set-idle-timeout status:ok`, the core's
  `screen-policy` and the shell's `idle-policy effective_secs:15`) and the
  screen blanked after 15 s idle; dragging the brightness rail to 0 gave

  store (persistence, holder release, watch), an end-to-end socket test of

  field, scenario `input` schema, Settings timeout cycle and labels. fmt,

  `just linux-check test` for the touched crates pass.
- **Limitations:** QEMU cannot show what a phone panel does on DPMS-off

### 2026-10-11 (Apps list fling with deceleration; QEMU/mock only)

- **Why:** the home Apps list scrolled only while the finger dragged (the
  limitation recorded in both 2026-10-11 entries below). No surface in the
  tree had fling or velocity code to reuse.
- **Shared helper:** `ferrix_ui::fling` (pure, time-injected). Release
  velocity is a least-squares slope over the samples in the last 100 ms;
  with fewer than two samples there (sparse input) it uses the last pair
  when they are at most 250 ms apart; a finger still for 50 ms before
  lifting releases at zero; samples at the same millisecond replace rather
  than add. The glide is `v0 * exp(-t / 325 ms)` and ends below 0.05 px/ms.
- **Input times:** `ClientHandler::input_time` (default no-op) now gets the
  Wayland timestamp of every touch down/motion/up and pointer
  press/motion/release before it is delivered, so velocity uses the
  compositor's event clock, not the time the client happened to dispatch a
  batch. Other surfaces are unchanged.
- **Launcher:** a list drag released faster than 0.1 panel heights/s glides
  on (capped at 4 heights/s). The runner's existing `deadline`/`timer`
  drives it at 16 ms frames, and it redraws only when the rounded offset
  changes; the timer is idle otherwise. The glide clamps and stops at either
  end with no overscroll, does not start when the drag already reached the
  end it would glide toward, ends when the list is left, and a touch on a
  gliding list stops it without tapping the row under it. Untimed input
  (tests without `set_time`) never flings, so plain drags behave as before.
  `apps-fling` (`scroll`, `velocity_px_s`) and `apps-fling-end` (`scroll`)
  records make the glide observable.
- **Evidence (QEMU, TCG, headless):** with a fresh `FERRIX_OUT_DIR`,
  `just qemu-build`, `just qemu-check` (`check-passed`) and
  `just qemu-gesture-check` (`gesture-check-passed`) pass at the versioned
  1080x2340 profile. The 8-entry QEMU list fits that panel and does not
  scroll there, so the fling was driven on a scratch copy of the profile
  with `height = 1200` (`FERRIX_QEMU_PROFILE`, not checked in) with
  `just qemu-swipe`-style QMP input (6 tablet motions 20 ms apart): a 40 px
  flick logged `apps-fling scroll:40 velocity_px_s:280` and then
  `apps-fling-end scroll:114`. The captured frame shows the list at that
  offset with the cursor ring where the finger lifted. Hard flicks that
  reached either end during the drag started no glide. **mock:** 7
  `ferrix-ui` fling tests (120 Hz speed, recent-window fit, jitter and
  duplicate times, sparse pairs, rest before lift, monotonic deceleration and
  settle time, min/max) and 5 launcher tests (glide and deceleration, clamp
  at both ends, stop-on-touch without tap, slow/paused/untimed drags, sparse
  QEMU-style input and leaving the list). fmt, workspace clippy (host and
  `just linux-check`) and `just linux-check test -p ferrix-ui -p
  ferrix-basic-screen` pass.
- **Limitations:** nothing has run on the Pixel 9a. The tuning (325 ms time
  constant, thresholds) is unvalidated by feel on a real panel; frames are
  timer-paced at 16 ms rather than synchronised to `wl_surface.frame`, and
  each frame re-composes the whole surface in software. Only the Apps list
  flings; Settings, Files and other lists still scroll by drag only.

### 2026-10-11 (Pixel 9a: AoC audio DSP firmware route; offline only, not yet booted)

  `audio_output_control` service is what the card waits for. Autoload is not
  an option here: `aoc_core` is first-stage, so it probes before the rootfs
  firmware exists. A second blocker: the card's haptics back end is
  `cs40l26-codec`, which registers only after `cs40l26.wmfw` loads at probe.
- **Change:** new controllers `audio-aoc` (`aoc.bin`), `audio-tas25xx`
  (`tismartpa_driver_tuning.bin`, the TAS2572 init sequences and profiles)
  and `haptics-cs40l26` (`cs40l26.wmfw`, wavetable, svc/dvl/dbc) in
  `firmware-stage-allowlist.tsv` and `firmware-policy.toml`. They are
  optional rows in the rootfs firmware allowlist. A new
  `ferrix-aoc-firmware` OpenRC one-shot writes `aoc.bin` once, only while
  `revision` reads `Offline`, and nothing `need`s it. Per-unit
  `speaker.cal`, the HAL-only `ti_sp_tuning.bin` and the `cs40l26-calib.*`
  pair are deliberately not staged.
- **Offline evidence:** the factory `aoc.bin` (signed release
  `16047897-polygon`) contains all 293 interface UUIDs that the pinned
  driver's `aoc-interface-zuma.h` checks. `firmware-workflow.sh`,
  `rootfs-workflow.sh`, `radio-firmware-runtime.sh` and the new
  `aoc-firmware-runtime.sh` pass on macOS. The last three also pass on the
  Linux builder. On the builder `firmware-workflow.sh` hits a GNU-grep `\t`
  check that already fails on `origin/pixel-9a-gpu`, so that failure is not
  from this change.
- **Limitations:** nothing has booted. GSA acceptance, AoC coming online,
  the card binding and any sound are all unproven. No UCM or mixer policy
  is set, so a PCM needs `TDM_0_RX Mixer EP1` and the `TAS25XX` switches set
  by hand. Speaker protection, which the Android HAL configures on the AoC
  DSP, is not configured, so speaker tests must stay at low level and short.
  `audio` stays `unsupported` in `capabilities.toml`. Device steps, risks
  and the stock mixer paths are in
  `targets/boards/google-pixel-9a-tegu-gxq96-mp1-0/audio-bringup.md`. No QEMU
  claim.

### 2026-10-11 (Android apps survive a ferrix-shell restart; host tests only)

- **Problem (physical `google-pixel-9a-tegu-gxq96-mp1-0`):** after
  `rc-service ferrix-product restart` Android apps never came back
  (Browser `crashed`, exit 1) until Waydroid was restarted. Waydroid binds
  the compositor socket *file* into the container at session start, so a
  restarted shell's new socket never reached Android's hwcomposer, whose
  upstream reconnect loop then spun forever.

  (Pixel initd and QEMU start script); `ferrix-waydroid.sh` binds that

  (`android-wayland-link`); `ferrix-appd` forgets surfaces when the
  compositor connection ends, keeping Android instances running
  (`appd-surfaces-reset`). Details: `docs/android-runtime.md` §7
  "Compositor restarts". No hwcomposer patch.
- **Evidence:** host only: `android-bootstrap-test.sh` (runs the link
  script against a fake container root), `dev-compose-android-contract.py`,
  `cargo test` (`ferrix-shell`, `ferrix-appd`), `just linux-check`. Not yet
  run on the device or QEMU.

### 2026-10-10 (Installed APKs as Ferrix apps; adopted task windows; mock)

  Ferrix app (ADR-008 "Installed APKs", owner decision (c)). The Android
  adapter reads `waydroid app list`; `ferrix-appd` lists each launchable
  package beside the checked-in catalog as `apk.<package>` (hashed suffix

  unknown composer window or a `not-installed` launch; changes publish
  `CatalogChanged` (record `installed-apps`, counts only).

  when its pid is one the runtime reports and its `app_id` names a
  launchable app (`Runtime::attach`, no relaunch; `app-adopting`,
  `android-app-attached`); raised when an Android app is in front (an
  intent from it), otherwise backgrounded until opened. This replaces the
  earlier limitation that such tasks stayed withheld.
- **Evidence:** `mock` only: `cargo test --workspace` (new tests in
  `ferrix-app-api`, `ferrix-runtime-android`, `ferrix-appd`,
  `ferrix-basic-screen`). No QEMU or physical run has listed or adopted

- **Limitations:** letter icons, not Android's bitmap icons; the home grid
  does not scroll; each poll is one `waydroid app list` subprocess.

### 2026-10-10 (Pixel 9a: stock Codec2 hardware video overlay for Waydroid; offline only, not yet booted)

- **What:** `tools/pixel-9a/waydroid-codec2-overlay.sh` extracts the stock
  CP3A Codec2 services from the pinned factory archive into an ignored
  overlay: Samsung Exynos MFC (`IComponentStore/default`, `c2.exynos.*`) and
  Google BigWave AV1 (`IComponentStore/default1`, `c2.google.av1.*`). Both are
  AIDL `android.hardware.media.c2` V2. The allowlist is
  `targets/boards/google-pixel-9a-tegu-gxq96-mp1-0/waydroid-codec2-overlay.tsv`.
  It adds generated `media_codecs{,_performance}_c2.xml` with no `.secure`
  codecs, ranks the hardware codecs 256, ahead of ffmpeg video (272) and the
  AOSP software codecs (512), and keeps both as fallback. It also writes a
  Ferrix VINTF fragment and `media.c2.hal.selection=aidl`. Nothing it
  installs replaces a Waydroid vendor file.
- **Private runtime:** stock `libcodec2_aidl_V2` needs
  `CreateCodec2BlockPool(C2PlatformAllocatorDescV2…)`, which only the stock
  `libcodec2_vndk` defines. Waydroid's `libcodec2_hidl`/`libcodec2_aidl`
  need symbols the stock copy lacks. So no copy of the library can serve
  both sides from `/vendor/lib64`. The stock closure (all but LL-NDK) goes to
  `/vendor/lib64/ferrix-codec2`, and the two services reach it only through
  `setenv LD_LIBRARY_PATH` in their rc files.
- **ABI check (offline):** `waydroid-mali-abi-check.sh` searches
  `lib64/ferrix-*` first. It passes against the 23.2 build
  (`20261010T070700Z` vendor.img) with system dirs `system/lib64`,
  `apex/com.android.runtime/lib64/bionic` and `apex/com.android.i18n/lib64`.
  Without the i18n dir it reports `libandroidicu.so` as missing, reached
  through system-internal `libmediandk` dependencies. The Mali overlay
  still passes.
- **Wiring (opt-in):** `dev-compose.py --codec2-overlay DIR --codecs hardware`
  (needs `--renderer mali` for gchips buffers) writes
  `/etc/ferrix/waydroid-codecs`. `ferrix-waydroid.sh` installs or removes the
  overlay next to the Mali one. It binds `/dev/{bigwave,g2d,fimg2d,m2m1shot_scaler0}`
  (optional) through `config_ferrix` and gives them to UID 1046 with mode
  0660; the container has no `lxc.idmap`, so that is Android's mediacodec.
  Waydroid already binds `/dev/video*` and `/dev/dma_heap/*` and sets them
  to 777. Covered by `android-bootstrap-test.sh`, the dev-compose contract
  (ext4 staging, on the builder), and `tools/pixel-9a/tests/waydroid-codec2-xml.sh`.
- **Limitations:** nothing has run on the device yet. It is unproven that
  the `exynos_mfc`/`bigwave`/`g2d`/`smfc` modules bind, that the services
  start under the container's minijail and seccomp, and that decoded frames
  display. `vendor.debug.c2.sbwc.enable=0` and `vendor.google.av1dec.afbc=0`
  are untested hints to keep decoder output linear. No `m2m1shot` scaler
  module was found in the Kleaf dist. `media.c2.hal.selection=aidl` also
  moves the container's software codecs onto their AIDL stores.
